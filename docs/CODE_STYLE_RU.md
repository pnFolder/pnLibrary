# Стиль исходного кода pnLibrary

Этот документ фиксирует визуальный и документальный стиль проекта. Его цель — чтобы код можно
было читать сверху вниз без расшифровки плотных конструкций.

## Аннотации

Аннотация всегда находится на отдельной строке непосредственно перед объявлением.

```kotlin
@Throws(IOException::class)
fun encrypt(payload: ByteArray, payloadFormat: String): String {
    // ...
}
```

Несколько аннотаций также записываются отдельно:

```kotlin
@JvmStatic
@JvmOverloads
fun from(version: MinecraftVersion, inclusive: Boolean = true): MinecraftVersionRange {
    // ...
}
```

Не используется плотная форма `@JvmStatic fun create(...)` или
`@Volatile private var state = ...`.

## Расстояние между объявлениями

- Между двумя методами, свойствами с отдельными смысловыми блоками и вложенными типами оставляется
  одна пустая строка.
- Внутри короткой связанной группы свойств пустые строки используются для разделения различного
  состояния, а не после каждой строки автоматически.
- Две и более пустые строки подряд не используются.
- Тело из нескольких действий раскрывается фигурными скобками вместо записи всей логики в одну
  строку.

```kotlin
@EventHandler
fun quit(event: PlayerQuitEvent) {
    sessions.remove(event.player.uniqueId)?.finish(notify = true)
}

@EventHandler
fun disable(event: PluginDisableEvent) {
    close(event.plugin)
}
```

## Перенос аргументов

Короткая сигнатура остаётся одной строкой. Длинная сигнатура переносится по одному параметру на
строку, с завершающей запятой. Перенос не должен скрывать тип или назначение параметра.

```kotlin
fun record(
    plugin: String,
    level: DiagnosticLevel,
    message: String,
    error: Throwable? = null,
)
```

## Выравнивание данных

Выравнивание допустимо в небольших таблицах однотипных присваиваний, когда оно помогает сравнивать
ключи и значения.

```kotlin
envelope["format"]           = FORMAT
envelope["version"]          = VERSION
envelope["contentAlgorithm"] = "A256GCM"
```

Не следует выравнивать несвязанные выражения через весь большой файл: изменение одного длинного
названия не должно переформатировать десятки строк.

## KDoc и Javadoc

Документация пишется на английском, сообщения сервера и пользовательская документация — на русском.

Документируются:

- все публичные классы, интерфейсы, перечисления и методы API;
- публичные параметры моделей через `@property`;
- нетривиальные внутренние компоненты и их жизненный цикл;
- ограничения потоков, ресурсов, безопасности и форматов;
- исключения и побочные эффекты, которые важны вызывающему коду.

Не нужно пересказывать очевидный приватный getter или каждую локальную переменную. Хороший комментарий
объясняет контракт и причину решения, а не переводит имя метода на английский.

```kotlin
/**
 * Creates a local support report from one consistent runtime snapshot.
 *
 * @throws IllegalStateException when the observability runtime is closed
 */
fun createReport(request: ObservabilityReportRequest): ObservabilityReport
```

## Проверка перед коммитом

Перед отправкой изменений нужно проверить:

1. нет ли аннотаций и объявлений на одной строке;
2. нет ли нескольких методов, сжатых в одну строку;
3. описан ли новый публичный API на английском;
4. обновлена ли профильная страница в `docs/`;
5. проходят ли `./gradlew test` и сборка платформенных JAR.
