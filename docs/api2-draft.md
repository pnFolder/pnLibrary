# API 2: черновик для обсуждения

Статус: набросок, кода нет. Ветка `next`. Цель: плагин подключается к pnLibrary одним блоком, всё остальное
закрывается само. Старый API остаётся рабочим, поверх нового ядра он станет тонкими адаптерами.

## Что неудобно сейчас

Из [docs/commands.md](commands.md), пример магазина:

- Подключение занимает семь шагов руками: `getOrNull`, проверка на `null` с отключением плагина,
  `plugins.register`, `registerModule`, потом уровни ошибок, потом команда.
- Каждую регистрацию (`CommandRegistration`, слушатели, задачи, конфиги) плагин хранит в полях и закрывает сам.
  Забыл закрыть — утечка при перезагрузке.
- Одна возможность живёт в трёх местах: `library.plugins`, `module.tasks`, `module.events`. Автор плагина
  должен помнить, где что.
- Java и Kotlin ведут себя по-разному: билдеры и `Consumer` у Java, лямбды с получателем у Kotlin.

## Как могло бы выглядеть

```kotlin
class ShopPlugin : JavaPlugin() {
    override fun onEnable() = pnPlugin(this) {
        // всё внутри закрывается само, когда плагин выключается

        config<ShopConfig>("config.yml")

        commands {
            command("shop") {
                permission("shop.use")
                executes { reply("Команды: /shop buy <товар>") }
                literal("buy") {
                    playerOnly()
                    argument("item", choice("sword", "apple", "bow")) {
                        executes { buy(get("item")) }
                    }
                }
            }
        }

        listen<PlayerBoughtEvent> { println(it.item) }

        every(5.minutes) { saveBalances() }

        stats {                      // попадает в /pn stats и в журнал
            gauge("balances") { balances.size }
        }
    }
}
```

Что здесь решено:

- **Одна точка входа** `pnPlugin(this) { ... }`. Нет `getOrNull`: если библиотеки нет, плагин получает понятную
  ошибку при старте, а не `null` по всему коду.
- **Всё внутри блока закрывается само.** Команды, слушатели, задачи, метрики привязаны к плагину.
- **Описываем, что нужно, а не как.** `every(5.minutes)` вместо `TaskSpec.builder()...`.
- **Один стиль для Kotlin и Java.** Для Java остаётся билдер с теми же именами.

## Что не меняется

- Права, ошибки по уровням (плагин, модуль, команда) и локализация остаются как есть.
- Бинарная совместимость: плагин, собранный на `0.0.1-dev.6`, запускается на новой версии без пересборки.
  Старые классы помечаются `@Deprecated(replaceWith = ...)` и работают через адаптеры.

## Адреса: плагин, модуль и всё, что нужно найти по имени

Решено (со слов пользователя): плагин можно зарегистрировать один, без модулей. Тогда у него есть модуль по
умолчанию `main`. Явные модули остаются по желанию.

Формат адреса (решено): модуль есть всегда. Если плагин зарегистрирован без модулей, у него один модуль `main`.

| Адрес | Значение |
|---|---|
| `pnclans/main:score` | плагин `pnclans`, модуль по умолчанию `main`, имя `score` |
| `pnclans/war:score` | плагин `pnclans`, модуль `war`, имя `score` |

- Адрес всегда полный из трёх частей: `плагин/модуль:имя`. Сокращений нет, поэтому двусмысленности нет.
- В идентификаторах и именах `/` и `:` запрещены. Нарушение даёт ошибку при регистрации.
- Префикс плагина подставляет библиотека, автор его не пишет и не может занять чужой.
- Для автора плагина без модулей `main` подставляется сам: он пишет только имя, адрес собирает библиотека.

### Схема для PlaceholderAPI

PlaceholderAPI делит текст `%...%` по первому `_`: слева идентификатор расширения, справа параметры
(проверено по его исходникам). Формат `%pnclans/war:score%` без `_` до нас не доходит. Поэтому наружу
плейсхолдеры публикуются в виде `%префикс_модуль~имя%`, а родной вид `pnclans/war:score` живёт только внутри
библиотеки, в конфигах и в нашем чате.

Префикс всегда задаёт человек. Автоматического префикса нет: плагин, у которого префикс не указан, в
PlaceholderAPI не публикуется, и ничего случайного там не появляется.

- Префикс указывает автор плагина в коде или админ сервера в настройках библиотеки (аннотацией конфига).
  Правила префикса: `a-z0-9-`, без `_` (PlaceholderAPI делит по нему), не короче 2 символов.
- Префикс не привязан к модулю. Модуль может зарегистрировать любое число плейсхолдеров, и они не обязаны
  лежать под одним префиксом. У плагина может быть несколько префиксов, на каждый одно расширение.
- Какие плейсхолдеры видны под префиксом, задаёт правило: «все плейсхолдеры плагина», «из модуля X» или
  список имён. Правило тоже указывается явно вместе с префиксом.
- Параметры: `модуль~имя`. Если правило сужено до одного модуля, можно писать просто `имя`.
  Знак `~` выбран потому, что его нет в именах, а `.` и `{}` в именах уже есть (`player.{name}`).
- Занятый префикс (два плагина выбрали один) находится при старте: второй не регистрируется, в журнал идёт
  понятная ошибка, сервер не падает.

| Указано | Видны | Вид в PlaceholderAPI | Родной адрес |
|---|---|---|---|
| префикс `clans`, все | все модули | `%clans_war~score%` | `pnclans/war:score` |
| префикс `war`, модуль `war` | модуль `war` | `%war_score%` | `pnclans/war:score` |

- Разбор идёт по реестру библиотеки, имена с `_` ничего не ломают.
- В именах плейсхолдеров остаются `.` и `{}` как сейчас, существующие ключи не ломаются.

### Общий прогон текста

Одна точка `render(text, player)`: сначала наши `{pnclans/war:score}`, затем оставшиеся `%...%` отдаются
PlaceholderAPI, если он установлен, всё нерешённое остаётся как есть. Нужен адаптер PlaceholderAPI для Bukkit
(в коде платформ его пока нет).

Что сейчас адресуется и как (находки по коду):

| Что | Сейчас | Проблема |
|---|---|---|
| Модуль (`ModuleId`) | локальный, `shop` | уникален только внутри плагина, чужой не найти |
| Плейсхолдер (`PlaceholderKey`) | строка `a-z0-9_.{}-` | общий для всех, префикс плагина не навязан |
| Расширение (`Expansion.id`) | строка | общий реестр, при совпадении исключение |
| Сервис (`ServiceManager`) | по классу | один провайдер на владельца, адреса нет |
| Задача (`TaskSpec.id`, `key`) | `TaskId` и `key` | нет единого вида |
| Команда (`CommandDefinition.name`) | имя | конфликт имён между плагинами решается отдельно |
| Действие (`Action`) | объект без имени | нельзя вызвать по имени из конфига |
| Метрики, кулдауны, события, проверки | имена/ключи в своих местах | свой формат у каждого |

Нюансы, которые надо решить:
- Имя плагина может смениться; адрес должен опираться на стабильный `PluginId`.
- Старые плагины с `Expansion.id = "foo"` получают префикс автоматически, пока их не переведут.
- Плейсхолдеры снаружи (PlaceholderAPI) ждут короткий вид `%плагин_имя%`: нужен перевод адреса.
- Вызов по имени (действия из конфига) требует реестра действий с адресами.
