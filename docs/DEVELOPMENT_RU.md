# Единый стандарт разработки pnLibrary

Этот документ задаёт общий стиль реализации новых возможностей и изменения существующих
модулей. Он одинаков для Kotlin- и Java-кода.

## 1. Сначала определить границу изменения

Перед написанием кода нужно ответить на четыре вопроса:

1. Это публичный API или внутренняя реализация?
2. К какому модулю относится ответственность?
3. Должна ли функция работать одинаково на Bukkit, BungeeCord и Velocity?
4. Как будет выглядеть поведение при ошибке, закрытии и перезапуске?

Публичные контракты размещаются в `modules/api`. Низкоуровневая общая реализация — в `modules/core`
или `modules/features`. Код конкретной платформы не должен попадать в общий модуль.

## 2. Порядок реализации задачи

Каждая функция проходит одну и ту же последовательность:

```text
требование
  ↓
контракт и модель данных
  ↓
проверки входных данных
  ↓
внутренняя реализация
  ↓
адаптеры платформ
  ↓
ошибки и закрытие ресурсов
  ↓
тесты
  ↓
Java/Kotlin-примеры и документация
```

Сначала фиксируется ожидаемое поведение тестом или спецификацией. Реализация не должна появляться
до того, как понятно, что именно считается корректным результатом.

## 3. Разделение слоёв

```text
api
├── интерфейсы и стабильные модели
├── builders для Java и Kotlin
└── исключения и состояния, видимые пользователю

core
├── orchestration и жизненный цикл
├── policy и валидация
├── хранение состояния
└── транзакции и восстановление

features
├── независимые подсистемы
├── сетевые клиенты и форматы
└── проверки целостности

platforms
├── Bukkit/Paper/Folia
├── BungeeCord
└── Velocity
```

API не знает о Bukkit, файловой системе сервера или конкретной сетевой библиотеке. Платформенный
адаптер переводит native-события в общий контракт. Core не должен делать небезопасные cast-операции
к классам платформы.

## 4. Правила публичного API

- Публичный метод должен иметь KDoc/JavaDoc.
- Названия и документация кода — на английском; сообщения администратору — на русском.
- Java-пользователь должен иметь статический factory/builder и понятные overload-методы.
- Коллекции, возвращаемые из API, неизменяемые или defensive-copy.
- Валидация выполняется на границе API: пустые строки, неправильные версии, URL, пути и диапазоны
  отклоняются сразу.
- Новые публичные типы требуют обновления API baseline и Java-теста.
- Не добавлять `@author` в каждый класс: авторство фиксируется Git-историей.
- Версия API pnLibrary изменяется только отдельным осознанным решением; текущая версия — `1`.

Пример документации класса:

```kotlin
/**
 * Coordinates one validated update plan for a plugin ecosystem.
 *
 * Platform-specific work is delegated to [PlatformAdapter]. This type owns
 * policy, state transitions and failure recovery, but never native casts.
 */
internal class PlanOrchestrator(...)
```

## 5. Состояния и ошибки

Долгие операции должны иметь явные состояния, например `DECLARED`, `DOWNLOADING`, `STAGED`,
`FAILED`, `CLOSED`. Ошибка не должна оставлять ресурс, временный файл или фоновый поток.

Каждый lifecycle-owner обязан быть idempotent:

- повторный `close()` безопасен;
- после `close()` новые операции отклоняются;
- временные файлы удаляются;
- незавершённая транзакция восстанавливается при следующем запуске.

## 6. Конфигурация и безопасность

Значение по умолчанию должно быть консервативным. Нельзя включать сетевую загрузку, внешний хост,
автоматическую установку или перезапуск только настройкой плагина. Администратор всегда имеет
последнее слово.

Для каждого внешнего файла нужно проверять:

- только HTTPS;
- разрешённый host;
- размер;
- SHA-256, когда файл устанавливается автоматически;
- безопасный путь назначения;
- соответствие манифесту компонента для pnLibrary-плагинов.

## 7. Тесты и проверка

Минимальный набор для новой подсистемы:

- позитивный сценарий;
- неправильный ввод;
- несовместимая версия/API;
- повторный вызов и закрытие;
- восстановление после ошибки;
- Java-вызов публичного API;
- отдельный тест для каждой платформенной границы, если она есть.

Перед коммитом выполняются:

```text
./gradlew clean test apiCheck :distribution:build
```

`apiCheck` обязателен даже для небольшого изменения публичного API. Нельзя считать задачу
завершённой при наличии незакоммиченных изменений или непроверенных тестов.

## 8. Коммиты и документация

Один коммит должен описывать одну логическую часть работы. Формат сообщения:

```text
feat(updates): add direct component deliveries
fix(commands): reject stale command plans
docs(api): explain Java registration
test(tasks): cover restart recovery
```

Вместе с публичным изменением обновляются README или профильная документация в `docs/`. Пример
должен быть копируемым и соответствовать реально существующим методам.

## 9. Definition of Done

Задача считается завершённой, если:

1. контракт понятен Java- и Kotlin-пользователю;
2. ответственность находится в правильном модуле;
3. ошибки, закрытие и перезапуск обработаны;
4. добавлены тесты и API baseline обновлён при необходимости;
5. документация не обещает несуществующую функцию;
6. полный Gradle-проверочный набор проходит;
7. рабочее дерево чистое, коммит создан и отправлен в GitHub.
