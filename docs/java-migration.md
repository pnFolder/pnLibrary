# Перенос pnLibrary с Kotlin на Java

**Завершён 2026-11-26.** `.kt` в репозитории нет, плагин Kotlin и stdlib убраны из сборки, `apiCheck` работает через задачи, зарегистрированные в корневом `build.gradle.kts`. Ниже правила, по которым писали код; для нового кода они остаются в силе.

Ветка `dev/java-rewrite`. Переносим модуль за модулем, сборка после каждого модуля зелёная.

## Порядок
`common` → `api` → `spi` → `features/*-api` → `features/*-runtime` → `updates` → платформы → `core`.
Модуль считается готовым, когда в нём нет `.kt` (основной код и тесты), `scripts/verify.sh` зелёный и сделан коммит.

## Правила Java (стиль Paper, байткод Java 8)
- Только Java 8: без `var`, `record`, `List.of`, `Optional.isEmpty`, текстовых блоков.
- Пакет и имя класса не меняем. Один тип в файле. Файл до 300 строк, метод до 30.
- Геттеры в стиле JavaBeans: `getName()`, `isEnabled()`, `hasX()`. Так Kotlin-код, который ещё не перенесён, видит их как свойства `name`, `isEnabled`, и менять его не надо. Не `name()`, не `uniqueId()`.
- Неизменяемая модель: `final` класс, `private final` поля, конструктор или `Builder`, `equals`/`hashCode`/`toString`. Вместо значений по умолчанию Kotlin: статические фабрики `of(...)` или перегрузки.
- Kotlin `object` → `final` класс с приватным конструктором и статическими методами. Kotlin `companion` → статические методы того же класса.
- Расширения и функции верхнего уровня → статические методы класса по смыслу (`AudienceIdentity.name(audience)`); вызовы в ещё не перенесённом Kotlin-коде поправить.
- Интерфейс-контракт: `@ApiStatus.NonExtendable`, если его реализует только библиотека. Необязательное умение — `default`-метод с «не умею».
- Аннотации `@NotNull`/`@Nullable` (org.jetbrains.annotations) на публичных параметрах и результатах.
- Без флагов в параметрах, без `Impl`/`Manager`/`Helper`/`Utils`. Зависимости через конструктор.
- Ошибки не глушим. `catch (Throwable)` только прибрать и пробросить.
- KDoc → Javadoc (`/** ... */`, `{@code}`, `<pre>{@code}`), пример на 3 строки в публичном API. Комментарии только «почему».
- Корутины, `sealed`, `inline`, `reified`: заменить обычными классами и Class-параметрами; если не получается, оставить место и записать в отчёт.
- Тесты переносим вместе с кодом (JUnit 5, Mockito), имена и проверки те же.

## Что нельзя
- Не менять поведение. Не добавлять возможностей. Не трогать `updates` и `remote` по смыслу (только язык).
- Не оставлять копии: старый `.kt` удаляем в том же коммите.

## Проверка
`scripts/verify.sh <модуль>` собирает весь проект (чтобы поймать Kotlin-вызовы к переписанному коду), гоняет тесты модуля и `apiCheck`.
После правок публичного API: `:modules:api:apiDump`, отдельным запуском `apiCheck`.
