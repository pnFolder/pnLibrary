# План упрощения архитектуры pnLibrary

## Цель

Сделать публичный путь использования библиотеки очевидным: разработчик работает с `PnLibrary` и сервисами, а платформенные адаптеры остаются внутренней реализацией.

Целевой пользовательский маршрут:

```text
Plugin -> PnLibrary -> Service -> Core -> Platform Bridge -> Bukkit/Bungee/Velocity API
```

## Правила изменений

- Не менять поведение без отдельного теста.
- Не удалять старые публичные API без миграционного периода.
- Платформенный код не должен протекать в обычные примеры.
- Каждый этап должен собираться и проходить тесты отдельно.
- Не смешивать упрощение API с крупной переработкой бизнес-логики.

## Фаза 1. Зафиксировать публичную поверхность — выполнено

1. Составить список классов, которые реально должны использовать потребители.
2. Разделить пакеты на `api`, `core`, `spi` и platform runtime.
3. Пометить внутренние контракты `internal`, где это возможно.
4. Добавить архитектурные тесты или проверки, запрещающие API зависеть от platform runtime.
5. Зафиксировать текущий baseline: `./gradlew check`.

Результат: понятно, какие классы являются продуктом, а какие — деталями реализации.
Дополнительно добавлена карта границ в [`architecture/OVERVIEW.md`](architecture/OVERVIEW.md).

## Фаза 2. Упростить создание `PnLibrary` — частично выполнено

1. Оставить один очевидный factory/entry point.
2. Спрятать создание Bukkit/Bungee/Velocity адаптеров внутри platform-модулей.
3. Убрать необходимость вручную собирать цепочку SPI для стандартного сценария.
4. Добавить по одному минимальному примеру для каждой платформы.

Результат:

```kotlin
val library = PnLibrary.create(this)
```

Внутренние команды и задачи библиотеки получили явно названные bound-входы
`library.registerRuntimeCommand(...)` и `library.runtimeTaskScope()`. Команды и
задачи consumer-плагина по-прежнему явно указывают владельца, чтобы их lifecycle
закрывался вместе с этим плагином. Автоматическое создание runtime-адаптера остаётся следующим
отдельным шагом.

## Фаза 3. Упростить командный API — выполнено для первого среза

1. Сделать `CommandService` главным публичным входом.
2. Описать регистрацию команды через единый DSL или builder.
3. Спрятать `NativeCommandRegistrar`, dispatcher и bridge из пользовательского кода.
4. Оставить платформам только преобразование native source и регистрацию native-команды.
5. Проверить единый сценарий на Bukkit, Bungee и Velocity.

Первый срез завершён: для внутренних ресурсов runtime добавлены явно названные
bound-регистрации, а consumer-команды сохранили явного lifecycle-владельца. Встроенные
команды и пользовательская документация разделяют эти два сценария, а
platform-specific registrar остаётся внутри runtime.

Целевой сценарий:

```kotlin
library.registerRuntimeCommand("kit") {
    execute { context -> context.reply("Вы получили набор") }
    suggest { listOf("starter", "vip") }
}
```

## Фаза 4. Сжать platform SPI — аудит выполнен

1. Найти интерфейсы, которые существуют только ради одной реализации.
2. Объединить мелкие capability-интерфейсы там, где отдельное расширение не нужно.
3. Оставить отдельными только реальные точки расширения: команды, задачи, аудитории, метрики и lifecycle.
4. Проверить зависимости между модулями и убрать циклические или лишние переходы.

Результат: меньше интерфейсов без потери расширяемости.

Аудит показал, что текущие platform-интерфейсы используются как capability-контракты
разными core-компонентами и не являются дубликатами платформенных реализаций. Их
механическое объединение увеличило бы связанные зависимости. Унификация оправдана
для повторяющегося native-кода команд и уже выполнена через generic adapter;
аудитории, задачи и lifecycle сохраняют отдельные границы из-за различающейся
native-семантики.

## Фаза 5. Переписать документацию и примеры — частично выполнено

1. Документация строится по пользовательским задачам, а не по внутренним классам.
2. Добавить карту архитектуры на одну страницу.
3. Для каждого сценария дать путь от публичного вызова до платформы.
4. Перевести примеры на новое API.
5. Отдельно документировать SPI для разработчиков интеграций.

Командные и task-примеры в `README.md`, `INTEGRATION.md` и `docs/COMMANDS.md` /
`docs/TASKS.md` разделяют runtime-owned и plugin-owned сценарии. В документацию
добавлено единое правило владения ресурсами; общая документация SPI и миграционные
заметки остаются отдельной задачей после стабилизации публичной поверхности.

## Фаза 6. Миграция и удаление legacy

1. Добавить новую систему рядом со старой.
2. Перевести внутренние использования и примеры.
3. Добавить deprecation с понятной заменой.
4. Подождать миграционный период.
5. Удалить старый API отдельным изменением.

## Критерии готовности

- Новый разработчик находит точку входа за одну минуту.
- Регистрация команды выглядит одинаково на всех платформах.
- Публичные примеры не импортируют SPI.
- `api` не зависит от platform runtime.
- Каждая фаза проходит `./gradlew check`.
- Для стандартного сценария не требуется знать внутренние адаптеры.

## Первый практический шаг

Начать с вертикального среза команд: сначала описать желаемый публичный `CommandService`, затем провести его через одну платформу и только после проверки распространить на остальные. Это даст измеримый результат и не позволит переписывать архитектуру вслепую.
