# Чистая архитектура observability

## Цель

Объединить диагностику, журнал событий, вложения и создание отчётов в одну читаемую систему `observability`. Код должен читаться сверху вниз, каждый класс должен иметь одну ответственность, а публичный API не должен требовать знания внутреннего формата хранения.

## Публичный API

Единственная рекомендуемая точка входа — `PnLibrary.observability`.

Основные операции:

- `capture { ... }` — записать событие, данные и связанные файлы;
- `failure(error) { ... }` — записать ошибку и её контекст;
- `status(plugin, component) { ... }` — обновить состояние компонента;
- `recent(query)` — получить последние записи;
- `createReport(request)` — собрать бинарный отчёт.

Пользователь не указывает `eventId`, MIME-типы, внутренние имена файлов и пути хранилища. Библиотека определяет и связывает их самостоятельно.

Существующие `PnLibrary.diagnostics` и `PnLibrary.activity` остаются временными совместимыми мостами. Они делегируют новой системе, помечаются устаревшими и не содержат собственной логики.

```text

modules/core/.../core/observability/

├── ObservationJournal.kt
├── AttachmentStore.kt
├── ComponentStatusRegistry.kt
├── BinaryReportBuilder.kt

```

Совместимые адаптеры старого API остаются в прежних пакетах до следующего несовместимого API-релиза.

## Ответственности

### ObservabilityRuntime

Координирует публичные операции. Нормализует ввод, передаёт запись в журнал, файлы — в `AttachmentStore`, состояния — в `ComponentStatusRegistry`, отчёт — в `BinaryReportBuilder`. Не содержит файлового формата и сериализации.

### ObservationJournal

Хранит ограниченную историю наблюдений и применяет внутреннюю политику срока хранения. Не знает о командах, платформах и создании отчётов.

### AttachmentStore

Проверяет файл, определяет его формат, считает SHA-256, сохраняет содержимое и возвращает метаданные. Удаляет вложения, когда связанная запись больше не хранится.

### ComponentStatusRegistry

Хранит последнее состояние компонентов и диагностические contributors. Снимок состояния формируется без файлового ввода-вывода.

### BinaryReportBuilder

Получает готовые снимки от журнала, хранилища вложений, реестра состояний и платформы. Собирает один архив и передаёт его существующему шифрованию и загрузке.

### ReportStore

Отвечает только за сохранение и получение сформированных отчётов.

## Поток данных

```text
capture / failure / status
             │
             ▼
    ObservabilityRuntime
       │      │      │
       ▼      ▼      ▼
   Journal  Attachments  Statuses
       └──────┬──────────┘
              ▼
     BinaryReportBuilder
              ▼
       encryption/upload
```

Диагностическая ошибка создаёт одну нормализованную запись. Отдельная дублирующая запись в другом журнале не создаётся.

## Хранение

Внутренние файлы находятся в `plugins/pnLibrary/observability/`:

```text
observability/
├── observations.jsonl
├── attachments.jsonl
├── attachments/
└── reports/
```

Политика хранения задаётся кодом библиотеки и не доступна пользователю через конфигурацию. Критические записи сохраняются бессрочно; остальные очищаются по уровню важности. Очистка записи атомарно удаляет связанные вложения и обновляет манифест.

## Читаемость кода

- один публичный тип на файл, если тип не является маленькой частью той же модели;
- методы преимущественно короче 30 строк;
- ранние возвраты вместо глубокой вложенности;
- именованные функции вместо цепочек с несколькими побочными эффектами;
- сериализация и файловый ввод-вывод изолированы от бизнес-логики;
- общие преобразования и правила находятся в одном месте;
- комментарии объясняют причину решения, а не пересказывают код;
- публичные названия описывают предметную область, внутренние форматы наружу не выходят.

## Совместимость

Старые интерфейсы компилируются и делегируют `ObservabilityRuntime`. Новые плагины используют только `PnLibrary.observability`. Удаление мостов допускается только в следующей несовместимой версии API.

## Ошибки и безопасность

- ошибка вложения не повреждает журнал и сообщает понятную причину;
- исполняемые файлы не принимаются;
- размер файлов и отчёта ограничен внутренними константами;
- чувствительные значения проходят существующую очистку;
- повреждённая строка журнала пропускается, остальные данные загружаются;
- незашифрованный отчёт не отправляется удалённо;
- сбой загрузки не удаляет локальный отчёт.

## Проверка

Тесты должны покрывать публичный DSL, совместимые мосты, восстановление после перезапуска, сроки хранения, удаление вложений, повреждённый журнал, пределы размера, формирование бинарного отчёта и единственность записи диагностического события.

Полная проверка включает тесты API, core, платформенных runtime-модулей и сборку Bukkit JAR.
