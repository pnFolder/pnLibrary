# pnLibrary Update System V2

## 1. Цель

Система обновлений должна находить не отдельный JAR, а **целостный совместимый набор версий** для pnLibrary и всех зарегистрированных плагинов.

Главное правило: ни один файл не устанавливается, пока система не доказала совместимость всего плана.

## 2. Источники истины

### Установленный продукт

При регистрации библиотека знает:

- ID плагина или модуля;
- установленную версию;
- поддерживаемый диапазон pnLibrary API;
- GitHub-репозиторий и канал обновлений;
- зависимости от других продуктов и внешних плагинов;
- платформу и версию Java текущего сервера.

### Опубликованный продукт

Каждый релизный JAR обязан содержать ровно один файл:

```text
META-INF/pnlibrary/component.json
```

Минимальная схема:

```json
{
  "schema": 1,
  "product": "acceptance",
  "version": "2.4.0-beta.1",
  "channel": "beta",
  "pnLibraryApi": {
    "minimum": 1,
    "maximum": 2
  },
  "java": {
    "minimum": 8,
    "maximum": null
  }
}
```

Имя asset, GitHub tag и встроенная версия обязаны совпадать. Несовпадение делает **только этот asset** непригодным, но не ломает проверку остальных релизов.

## 3. Когда выполняется проверка

- один раз после регистрации всех плагинов при запуске сервера;
- периодически через интервал, заданный разработчиком библиотеки (например, 6 часов);
- вручную командой администратора;
- после регистрации или удаления продукта, если изменился граф зависимостей.

Ручная команда всегда запрашивает GitHub заново. Фоновая проверка может использовать свежий кэш.

Одновременно для одного репозитория выполняется только один сетевой запрос. Остальные проверки присоединяются к уже выполняющейся операции.

## 4. Два режима проверки

### Проверка конкретного плагина

```text
/pn update acceptance
```

Сначала проверяется только `acceptance`. Другой сломанный релиз не должен мешать показать результат для него.

Если найденное обновление требует другую версию pnLibrary API, проверка расширяется до необходимого графа:

```text
acceptance → pnLibrary → остальные затронутые плагины
```

### Полная проверка

```text
/pn update-status
автоматическая проверка
```

Проверяется весь зарегистрированный граф и строится единый план.

## 5. Поиск совместимого плана

Алгоритм не должен обновлять продукты по одному. Он решает задачу совместимости целиком.

1. Снять неизменяемый snapshot всех установленных продуктов.
2. Получить список GitHub Releases для каждого уникального репозитория.
3. Отфильтровать релизы по разрешённому каналу.
4. Найти assets, подходящие по имени, платформе и Java.
5. Проверить встроенный `component.json` каждого кандидата.
6. Добавить установленную версию каждого продукта как допустимый вариант «не обновлять».
7. Попробовать выбрать максимально новые версии, удовлетворяющие всем ограничениям.
8. Если плагину нужен более новый pnLibrary API — добавить обновление pnLibrary.
9. После выбора новой pnLibrary проверить каждый зависящий от неё плагин.
10. Если плагин не поддерживает новый API — найти совместимое обновление этого плагина.
11. Повторять расширение графа до стабильного результата.
12. Если совместимого набора нет — ничего не скачивать и показать точную причину.

Это лучше реализовать как поиск согласованного набора версий, а не рекурсивное обновление «по кругу».

## 6. Пример

Установлено:

```text
pnLibrary 2.2       предоставляет API 1
pnAuth    2.4       поддерживает API 1
pnCases   3.1       поддерживает API 1
```

Найдено:

```text
pnAuth 3.0          требует API 2
pnLibrary 3.0       предоставляет API 2
pnCases 3.1         поддерживает только API 1
pnCases 3.2         поддерживает API 1–2
```

Итоговый план:

```text
pnAuth    2.4 → 3.0
pnLibrary 2.2 → 3.0
pnCases   3.1 → 3.2
```

Если `pnCases 3.2` не существует, автоматическая установка запрещается. Администратор получает объяснение, что `pnCases 3.1` блокирует переход pnLibrary на API 2.

## 7. Поведение при ошибках релиза

Ошибки одного релиза изолируются:

- неверная встроенная версия — кандидат пропускается;
- неверный product ID — кандидат пропускается;
- отсутствует descriptor — кандидат пропускается;
- неподходящая Java или платформа — нормальная несовместимость, не ошибка;
- повреждённый JAR — кандидат помещается в карантин;
- HTTP timeout — выполняются ограниченные повторные попытки;
- недоступен GitHub — используется только ещё действительный кэш, иначе показывается сетевая ошибка.

Сломанный `pnLibrary 2.5.0` не должен мешать проверить `acceptance`, если обновление acceptance не требует именно этот релиз библиотеки.

## 8. Сеть и кэш

- отдельные таймауты подключения и чтения;
- не более 2–3 попыток с небольшой задержкой;
- GitHub API кэшируется по репозиторию;
- descriptor кандидата кэшируется по GitHub asset ID и digest;
- повторно не скачивать один и тот же большой JAR ради чтения метаданных;
- ручная проверка обновляет каталог GitHub, но может повторно использовать descriptor неизменившегося asset;
- ошибки и успешные ответы не должны навечно сохраняяться в одном кэше.

### 8.1. История релизов не ограничивается числом или возрастом

Нельзя использовать правила вроде:

```text
только последние 30 релизов
только релизы за последний месяц
только релизы за последний год
```

Стабильный релиз может быть старше сотен beta/dev-сборок. Поэтому время публикации и фиксированное количество записей не являются условием завершения поиска.

GitHub Releases API читается страницами по 100 записей. Клиент следует пагинации GitHub, пока не достигнет конца истории или уже сохранённой границы синхронизации.

### 8.2. Постоянный локальный индекс

Для каждого GitHub-репозитория хранится индекс всех уже известных релизов:

```text
updates/catalog/<owner>/<repository>/
  repository.json
  pages/
  releases.jsonl
  assets.jsonl
  descriptors/
  invalid-assets.jsonl
```

Индекс содержит:

- GitHub release ID;
- tag;
- draft/prerelease;
- дату публикации и изменения;
- asset ID, имя, размер и digest;
- вычисленный канал;
- результат проверки descriptor;
- причину отклонения повреждённого asset.

Это файловый индекс, а не отдельная база данных.

### 8.3. Первая и последующие синхронизации

Первая синхронизация:

1. Читать все страницы GitHub Releases.
2. Не держать всю историю одновременно в памяти.
3. Обрабатывать страницы последовательно и сохранять индекс на диск.
4. После завершения построить отдельные сортированные представления по product и channel.

Последующая синхронизация:

1. Начать с первой страницы GitHub.
2. Сохранять новые или изменённые release/asset.
3. Продолжать страницы до устойчивой границы уже известной истории.
4. Не загружать повторно неизменившиеся страницы и descriptors.
5. Периодически выполнять полную сверку, чтобы обнаруживать удалённые или отредактированные старые релизы.

HTTP cache validators (`ETag`/`If-None-Match`, когда они доступны) используются для ответа `304 Not Modified` без повторной передачи JSON.

### 8.4. Индекс каналов

После синхронизации релизы группируются отдельно:

```text
STABLE → стабильные версии
BETA   → beta + stable
ALPHA  → alpha + beta + stable
DEV    → dev + alpha + beta + stable
```

Внутри группы версии сортируются по `SemanticVersion`, а не по времени публикации и не по порядку ответа GitHub.

Поэтому сценарий:

```text
2.4.0 stable
40 последующих beta-релизов
```

не скрывает `2.4.0`: stable остаётся в своём индексе и доступен клиенту с каналом `STABLE`.

### 8.5. Ленивое чтение JAR

Полный список GitHub Releases можно получить без скачивания всех JAR.

1. Сначала индексируются только JSON GitHub и сведения об assets.
2. Assets фильтруются по product, имени, платформе, Java и каналу.
3. Кандидаты сортируются по semantic version.
4. Встроенный descriptor скачивается и проверяется начиная с наиболее подходящих кандидатов.
5. Если кандидат битый или несовместимый, поиск продолжается к следующему.
6. Проверенный descriptor сохраняется по asset ID + digest и больше не скачивается, пока asset не изменился.
7. Поиск старых кандидатов продолжается столько, сколько требуется resolver-у для нахождения совместимого плана.

Так история может быть очень большой, но сетевой трафик на JAR расходуется только на реальные кандидаты.

### 8.6. Условия остановки поиска

Поиск нельзя прекращать из-за даты или количества релизов. Он прекращается только когда:

- найден доказанно совместимый набор версий;
- достигнут конец проиндексированной истории и решения нет;
- пользователь отменил операцию;
- GitHub недоступен и локального индекса недостаточно для доказанного результата.

Найденный первый рабочий вариант не всегда является итоговым. Resolver сначала пытается найти максимально новый совместимый набор, используя semantic version и политику каналов.

### 8.7. Ограничения ресурсов

Большая история обрабатывается потоково:

- страницы GitHub не накапливаются целиком в памяти;
- повторяющиеся репозитории синхронизируются один раз;
- количество одновременно скачиваемых JAR ограничено;
- кэш имеет контроль целостности и удаляет только данные assets, которых больше нет на GitHub;
- диагностический журнал ограничивается по размеру, но индекс релизов не обрезается по возрасту;
- rate limit GitHub считается частью состояния и показывается администратору отдельно от timeout.

## 9. Скачивание и установка

После построения плана:

1. Скачать все JAR во временную staging-папку.
2. Проверить размер и SHA-256, полученные от GitHub.
3. Повторно прочитать встроенный descriptor.
4. Проверить product, version, API, Java и платформу.
5. Только после успешной проверки всех файлов создать одну транзакцию.
6. Подготовить все файлы к одному полному перезапуску.
7. Не применять частичный план.

## 10. Запуск после обновления

После перезапуска библиотека сравнивает реально загруженные версии с журналом транзакции:

- всё совпало — транзакция отмечается успешной, показывается одно итоговое сообщение;
- что-то не загрузилось — автоматический откат не выполняется;
- администратору показывается причина и команда ручного отката;
- резервные JAR сохраняются до подтверждения здоровья нового набора.

## 11. Политики

### pnLibrary

- проверка обновлений выполняется всегда;
- автоматическую загрузку можно временно отключить;
- критическое обновление может игнорировать паузу только после отдельного явно описанного правила;
- без совместимого графа библиотека ничего не устанавливает.

### Плагины

- обновление конкретного плагина можно приостановить на ограниченный срок;
- можно приостановить отдельный модуль плагина;
- истёкшая пауза автоматически перестаёт действовать;
- интервал проверки не настраивается пользователем.

## 12. Состояния результата

Каждая проверка заканчивается одним понятным состоянием:

```text
UP_TO_DATE       обновлений нет
UPDATE_AVAILABLE совместимый план найден
UPDATE_STAGED    файлы проверены и подготовлены
BLOCKED          план существует, но заблокирован зависимостью или политикой
INCOMPATIBLE     опубликованные версии не образуют совместимый набор
NETWORK_FAILED   GitHub недоступен и подходящего кэша нет
FAILED           внутренняя ошибка системы
```

Ошибки отдельных кандидатов хранятся как диагностика и не превращают всю проверку в `FAILED`, пока остаются другие кандидаты.

## 13. Команды

```text
/pn update-status
/pn update-status <plugin>
/pn update <plugin>
/pn update-confirm <token>
/pn update-rollback
```

`/pn update <plugin>`:

1. принудительно обновляет каталог нужного репозитория;
2. ищет обновление указанного продукта;
3. расширяет план только необходимыми зависимостями;
4. показывает весь итоговый план до установки;
5. скачивает план только после разрешения политики или подтверждения администратора.

## 14. Этапы реализации

1. Разделить API на `checkAll()` и `checkProduct(productId)`.
2. Ввести неизменяемый `UpdateCheckRequest` и результат проверки.
3. Сделать загрузку каталогов по уникальным GitHub-репозиториям.
4. Изолировать ошибки release/asset и собирать диагностику кандидатов.
5. Переписать resolver как поиск согласованного набора версий.
6. Добавить расширение графа через pnLibrary API и зависимости продуктов.
7. Отделить проверку от staging и установки.
8. Укрепить сетевой слой: retry, timeout, дедупликация запросов и кэш asset metadata.
9. Обновить Bukkit-команды и красивые сообщения.
10. Удалить старый глобальный сценарий `checkNow()` из команды конкретного плагина.
11. Добавить unit-тесты resolver-а и интеграционные тесты GitHub-каталога.
12. Собрать acceptance JAR и проверить полный сценарий на тестовом сервере.

## 15. Обязательные тестовые сценарии

- обновление одного плагина без изменения pnLibrary;
- обновление плагина вместе с pnLibrary;
- каскадное обновление нескольких зависимых плагинов;
- отсутствие совместимой версии одного зависимого плагина;
- битый старый релиз при наличии исправного нового;
- битый релиз другого продукта;
- разные каналы stable/beta/alpha/dev;
- несовместимые Java и платформа;
- GitHub timeout и повторная попытка;
- использование свежего кэша без сети;
- атомарная загрузка нескольких JAR;
- ошибка одного файла без частичной установки;
- подтверждение после перезапуска;
- ручной rollback;
- истечение временной паузы обновлений.

## 16. Критерий готовности

Система считается готовой, когда администратор может по любому результату понять:

- что установлено сейчас;
- что найдено;
- какой полный набор предлагается;
- почему он совместим или заблокирован;
- какие файлы будут заменены;
- требуется ли перезапуск;
- как выполнить ручной откат.
